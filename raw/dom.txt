class="ProseMirror content-xaiQhS leading-relaxed"><h1 dir="auto"><span>HANDOFF PROTOCOL</span></h1><table><tbody><tr><th><span>Metadata</span></th><th><span>Value</span></th></tr><tr><td><span>Document ID</span></td><td><code dir="ltr"><span>HANDOFF_PROTOCOL</span></code></td></tr><tr><td><span>Document Type</span></td><td><span>Workflow Protocol</span></td></tr><tr><td><span>Document Status</span></td><td><code dir="ltr"><span>DRAFT</span></code></td></tr><tr><td><span>Document Version</span></td><td><span>待确定</span></td></tr><tr><td><span>Compatible Framework Version</span></td><td><span>待绑定</span></td></tr><tr><td><span>Document Owner</span></td><td><span>待指定 Role</span></td></tr><tr><td><span>Editor</span></td><td><span>待明确授权</span></td></tr><tr><td><span>Approver</span></td><td><span>Framework Owner</span></td></tr></tbody></table><h2 dir="auto"><span>1. Purpose</span></h2><p dir="auto"><span>Handoff Protocol 定义 AI Software Engineering Framework 中的工作交接机制。</span></p><p dir="auto"><span>当一个 Role 的执行主体发生更换，或者尚未完成的工作需要移交时，通过 Handoff 将当前工作进度、实际工作现场、技术发现和未解决事项传递给接替 Agent。</span></p><p dir="auto"><span>Handoff 的目标是使接替 Agent 能够准确理解当前工作状态，并在完成必要核对后继续剩余工作。</span></p><h2 dir="auto"><span>2. Core Principles</span></h2><ol start="1" data-spread="false" style="--rich-text-list-marker-width: 1ch;"><li><p dir="auto"><strong><span>Owner-Driven Handoff</span></strong><span>：Handoff 由 Owner 主导，Agent 不通过自主协商完成交接。</span></p></li><li><p dir="auto"><strong><span>Document-Driven Handoff</span></strong><span>：正式交接必须具有独立的 Handoff Document。</span></p></li><li><p dir="auto"><strong><span>Task State Consistency</span></strong><span>：Task Card 和 Work Step 是 Task 执行进度的正式记录来源。</span></p></li><li><p dir="auto"><strong><span>Workspace as Evidence</span></strong><span>：项目实际工作区是判断实际修改状态的重要依据。</span></p></li><li><p dir="auto"><strong><span>Explicit Uncertainty</span></strong><span>：无法确认的修改和状态必须明确标记，不得猜测。</span></p></li><li><p dir="auto"><strong><span>Historical Preservation</span></strong><span>：每次 Handoff 创建独立记录，不覆盖历史交接记录。</span></p></li><li><p dir="auto"><strong><span>Separation of Responsibilities</span></strong><span>：Handoff 不替代 Task Protocol、Memory、Project Baseline 或 Approval Protocol。</span></p></li></ol><h2 dir="auto"><span>3. Handoff Triggers</span></h2><p dir="auto"><span>Handoff 仅适用于以下两种情况。</span></p><h3 dir="auto"><span>3.1 Agent Replacement</span></h3><p dir="auto"><span>Owner 主动决定更换当前 Role 的执行 Agent。</span></p><p dir="auto"><span>原 Agent 应整理当前工作状态，并创建 Handoff Document。</span></p><h3 dir="auto"><span>3.2 Incomplete Work Transfer</span></h3><p dir="auto"><span>当前工作尚未完成，需要由另一个 Agent 接手。</span></p><p dir="auto"><span>此情况包括原 Agent 正常结束工作后移交，以及原 Agent 异常中断后由接替 Agent 恢复工作现场。</span></p><p dir="auto"><span>异常中断不是独立的第三种 Handoff 类型，而是未完成工作移交的一种特殊情形。</span></p><h2 dir="auto"><span>4. Handoff Document Management</span></h2><h3 dir="auto"><span>4.1 Document Creation</span></h3><p dir="auto"><span>每次实际发生 Handoff，必须创建一份独立的 Handoff Document。</span></p><p dir="auto"><span>Handoff Document 存放在所属 Task 的 </span><code dir="ltr"><span>HANDOFFS/</span></code><span> 目录中。</span></p><pre><code class="language-text"><span>TASKS/
└── TASK-001/
    ├── TASK_CARD.md
    └── HANDOFFS/
        ├── HANDOFF-001.md
        ├── HANDOFF-002.md
        └── HANDOFF-003.md</span></code></pre><h3 dir="auto"><span>4.2 Unique Identification</span></h3><p dir="auto"><span>Handoff Document 使用文件名中的编号作为唯一标识。</span></p><p dir="auto"><span>例如：</span></p><ul data-spread="false"><li><p dir="auto"><code dir="ltr"><span>HANDOFF-001.md</span></code></p></li><li><p dir="auto"><code dir="ltr"><span>HANDOFF-002.md</span></code></p></li></ul><p dir="auto"><span>正文不需要重复记录 Handoff ID。</span></p><h3 dir="auto"><span>4.3 Historical Records</span></h3><p dir="auto"><span>每次 Handoff 都必须保留独立记录。</span></p><p dir="auto"><span>后续发生新的 Handoff 时，创建新的文档，不覆盖旧文档，也不重新打开已经完成的 Handoff。</span></p><h3 dir="auto"><span>4.4 Task Card Reference</span></h3><p dir="auto"><span>Task Card 负责关联所属 Task 的 Handoff Documents。</span></p><p dir="auto"><span>Task Card 不承担完整交接内容的记录职责。</span></p><h2 dir="auto"><span>5. Continuous Progress Recording</span></h2><p dir="auto"><span>Task 执行期间必须持续维护正式工作记录，不得将所有进度记录推迟到发生 Handoff 时才处理。</span></p><ol start="1" data-spread="false" style="--rich-text-list-marker-width: 1ch;"><li><p dir="auto"><span>Work Step 完成或状态发生变化时，按照 Work Step Protocol 更新 Task Card 中的执行进度。</span></p></li><li><p dir="auto"><span>执行期间的重要成果、代码修改、技术发现和验证结果应及时记录。</span></p></li><li><p dir="auto"><span>只有实际发生 Handoff 时，才创建正式 Handoff Document。</span></p></li><li><p dir="auto"><span>Task 完成不自动触发 Handoff Document 创建。</span></p></li><li><p dir="auto"><span>Handoff Document 汇总交接时需要的信息，但不替代 Task Card 中的持续执行记录。</span></p></li></ol><p dir="auto"><span>Task Card 和 Handoff Document 的职责区别：</span></p><ul data-spread="false"><li><p dir="auto"><span>Task Card：持续维护 Task 正式状态和执行进度。</span></p></li><li><p dir="auto"><span>Handoff Document：记录某次交接发生时的状态快照及交接所需信息。</span></p></li></ul><h2 dir="auto"><span>6. Handoff Document Structure</span></h2><p dir="auto"><span>每份 Handoff Document 必须遵循 </span><code dir="ltr"><span>HANDOFF_RECORD.md</span></code><span> 定义的结构。</span></p><table><tbody><tr><th><span>Section</span></th><th><span>Responsibility</span></th></tr><tr><td><span>Handoff Metadata</span></td><td><span>记录交接时间、交接原因和 Handoff 状态</span></td></tr><tr><td><span>Task Reference</span></td><td><span>记录交接发生时的 Task 状态快照</span></td></tr><tr><td><span>Work Progress</span></td><td><span>记录未完成的 Work Steps、当前进度和后续待执行事项</span></td></tr><tr><td><span>Modified Artifacts</span></td><td><span>记录与未完成工作有关的已修改文件、模块和函数及其修改状态</span></td></tr><tr><td><span>Technical Findings</span></td><td><span>记录执行期间发现的重要技术事实和结论</span></td></tr><tr><td><span>Validation Status</span></td><td><span>记录构建、测试和其他验证结果</span></td></tr><tr><td><span>Outstanding Issues</span></td><td><span>记录尚未解决的问题、阻塞和风险</span></td></tr><tr><td><span>References</span></td><td><span>引用需要阅读的正式文档、决策和其他记录</span></td></tr></tbody></table><h3 dir="auto"><span>6.1 Task State Snapshot</span></h3><p dir="auto"><span>Task Reference 必须反映 Handoff 实际发生时的 Task 状态。</span></p><p dir="auto"><span>它是一个具有明确时间点的状态快照，不得随着 Task 后续状态变化而被覆盖。</span></p><h3 dir="auto"><span>6.2 Work Progress</span></h3><p dir="auto"><span>Work Progress 只记录尚未完成的工作，包括：</span></p><ul data-spread="false"><li><p dir="auto"><span>未完成的 Work Steps。</span></p></li><li><p dir="auto"><span>各项工作的当前进度。</span></p></li><li><p dir="auto"><span>已经完成的部分。</span></p></li><li><p dir="auto"><span>尚待执行的事项。</span></p></li></ul><p dir="auto"><span>不需要重复列出已经完成的全部 Work Steps。</span></p><p dir="auto"><span>不单独设置 </span><code dir="ltr"><span>Next Actions</span></code><span>，后续待执行事项统一记录在 Work Progress 中。</span></p><h3 dir="auto"><span>6.3 Modified Artifacts</span></h3><p dir="auto"><span>Modified Artifacts 只记录与未完成工作有关的修改。</span></p><p dir="auto"><span>需要说明相关文件、模块或函数的修改情况及其当前状态。</span></p><p dir="auto"><span>不得因为某项修改已经存在，就直接认定其已经完成。</span></p><h3 dir="auto"><span>6.4 Validation Status</span></h3><p dir="auto"><span>必须区分实际验证结果和未经验证的状态。</span></p><p dir="auto"><span>例如：</span></p><ul data-spread="false"><li><p dir="auto"><span>代码已经修改不代表构建通过。</span></p></li><li><p dir="auto"><span>构建通过不代表测试通过。</span></p></li><li><p dir="auto"><span>没有验证记录不代表验证通过。</span></p></li></ul><h2 dir="auto"><span>7. Handoff Creation Responsibility</span></h2><h3 dir="auto"><span>7.1 Normal Handoff</span></h3><p dir="auto"><span>原 Agent 负责：</span></p><ol start="1" data-spread="false" style="--rich-text-list-marker-width: 1ch;"><li><p dir="auto"><span>整理当前 Task 和 Work Step 进度。</span></p></li><li><p dir="auto"><span>整理与未完成工作有关的修改。</span></p></li><li><p dir="auto"><span>记录重要技术发现。</span></p></li><li><p dir="auto"><span>记录构建、测试及其他验证结果。</span></p></li><li><p dir="auto"><span>记录未解决问题和风险。</span></p></li><li><p dir="auto"><span>创建 Handoff Document。</span></p></li><li><p dir="auto"><span>将 Handoff 状态设置为 </span><code dir="ltr"><span>PREPARED</span></code><span>。</span></p></li></ol><h3 dir="auto"><span>7.2 Abnormal Handoff</span></h3><p dir="auto"><span>当原 Agent 无法正常完成交接时，接替 Agent 必须先执行 Working State Recovery。</span></p><p dir="auto"><span>完成恢复后，由接替 Agent 创建 Handoff Document，并将其状态设置为 </span><code dir="ltr"><span>PREPARED</span></code><span>。</span></p><p dir="auto"><span>异常交接必须明确区分：</span></p><ul data-spread="false"><li><p dir="auto"><span>原 Agent 已经留下的记录。</span></p></li><li><p dir="auto"><span>接替 Agent 通过工作现场检查恢复的信息。</span></p></li><li><p dir="auto"><span>仍然无法确认的信息。</span></p></li></ul><p dir="auto"><span>不得将接替 Agent 恢复后补充的信息伪装成原 Agent 的交接说明。</span></p><p dir="auto"><span>异常情况必须在 Handoff Metadata 的交接原因中注明。</span></p><h2 dir="auto"><span>8. Working State Recovery</span></h2><h3 dir="auto"><span>8.1 Trigger</span></h3><p dir="auto"><span>当原 Agent 异常中断，无法提供完整、可靠的交接记录时，接替 Agent 必须执行 Working State Recovery。</span></p><h3 dir="auto"><span>8.2 Recovery Procedure</span></h3><p dir="auto"><span>接替 Agent 必须：</span></p><ol start="1" data-spread="false" style="--rich-text-list-marker-width: 1ch;"><li><p dir="auto"><span>阅读 Owner 指定的交接文档（如果存在）。</span></p></li><li><p dir="auto"><span>阅读相关 Task Card、Memory 和其他已有记录。</span></p></li><li><p dir="auto"><span>检查项目实际工作区。</span></p></li><li><p dir="auto"><span>识别已有记录中没有记录的修改。</span></p></li><li><p dir="auto"><span>区分已完成、未完成和意图不明确的修改。</span></p></li><li><p dir="auto"><span>检查构建、测试及其他验证状态。</span></p></li><li><p dir="auto"><span>整理恢复结果。</span></p></li><li><p dir="auto"><span>对无法确认的修改和状态向 Owner 报告。</span></p></li><li><p dir="auto"><span>根据恢复结果创建 Handoff Document。</span></p></li></ol><h3 dir="auto"><span>8.3 Workspace Inspection</span></h3><p dir="auto"><span>工作现场检查至少包括：</span></p><ul data-spread="false"><li><p dir="auto"><span>Git 工作区状态。</span></p></li><li><p dir="auto"><span>已修改、已暂存和未跟踪文件。</span></p></li><li><p dir="auto"><span>文件差异。</span></p></li><li><p dir="auto"><span>函数和模块的实际实现进度。</span></p></li><li><p dir="auto"><span>构建状态。</span></p></li><li><p dir="auto"><span>测试状态。</span></p></li><li><p dir="auto"><span>文档与代码的一致性。</span></p></li></ul><h3 dir="auto"><span>8.4 Recovery Rules</span></h3><p dir="auto"><span>必须遵循以下规则：</span></p><ul data-spread="false"><li><p dir="auto"><span>代码发生变化不代表代码已经完成。</span></p></li><li><p dir="auto"><span>没有记录在交接文档中，不代表修改可以忽略。</span></p></li><li><p dir="auto"><span>不得擅自回滚无法确认意图的修改。</span></p></li><li><p dir="auto"><span>不得擅自覆盖无法确认的修改。</span></p></li><li><p dir="auto"><span>不得将无法确认的修改直接视为正确成果。</span></p></li><li><p dir="auto"><span>重大差异和无法确认的信息必须向 Owner 报告。</span></p></li></ul><h3 dir="auto"><span>8.5 Recovery and Formal Records</span></h3><p dir="auto"><span>Working State Recovery 负责恢复和描述实际工作现场，不负责自动批准或修订正式项目结论。</span></p><p dir="auto"><span>如果恢复过程中发现正式需求、架构、接口或技术决策与实际实现存在冲突，必须按照现有 Framework 的变更和 Approval 规则处理。</span></p><h2 dir="auto"><span>9. Handoff Lifecycle</span></h2><p dir="auto"><span>Handoff 只有两个状态。</span></p><h3 dir="auto"><span>9.1 PREPARED</span></h3><p dir="auto"><span>表示 Handoff Document 已经创建，等待接替 Agent 接收。</span></p><ul data-spread="false"><li><p dir="auto"><span>正常交接：由原 Agent 创建 </span><code dir="ltr"><span>PREPARED</span></code><span> 记录。</span></p></li><li><p dir="auto"><span>异常交接：由完成 Working State Recovery 的接替 Agent 创建 </span><code dir="ltr"><span>PREPARED</span></code><span> 记录。</span></p></li></ul><h3 dir="auto"><span>9.2 ACCEPTED</span></h3><p dir="auto"><span>表示接替 Agent 已经完成交接内容的阅读、必要核对，并明确接受后续工作。</span></p><p dir="auto"><code dir="ltr"><span>ACCEPTED</span></code><span> 是单次 Handoff 的终态。</span></p><p dir="auto"><span>后续工作进度由 Task Card 和 Work Step 记录，不继续修改该 Handoff 的生命周期状态。</span></p><h3 dir="auto"><span>9.3 State Transition</span></h3><pre><code class="language-text"><span>PREPARED → ACCEPTED</span></code></pre><p dir="auto"><span>不定义其他 Handoff 状态。</span></p><h2 dir="auto"><span>10. Handoff Acceptance Requirements</span></h2><p dir="auto"><span>接替 Agent 将 Handoff 状态设置为 </span><code dir="ltr"><span>ACCEPTED</span></code><span> 前，必须完成：</span></p><ol start="1" data-spread="false" style="--rich-text-list-marker-width: 1ch;"><li><p dir="auto"><span>阅读并理解 Handoff Document。</span></p></li><li><p dir="auto"><span>核对项目实际工作现场。</span></p></li><li><p dir="auto"><span>确认已有修改及其完成状态。</span></p></li><li><p dir="auto"><span>了解构建、测试及其他验证结果。</span></p></li><li><p dir="auto"><span>了解尚未解决的问题、阻塞和风险。</span></p></li></ol><p dir="auto"><span>如果核对发现重大差异或无法确认的修改，必须向 Owner 报告，不得直接标记为 </span><code dir="ltr"><span>ACCEPTED</span></code><span>。</span></p><p dir="auto"><span>Owner 对相关事项作出处理决定后，接替 Agent 根据 Owner 的决定继续完成必要核对。满足接收条件后，才能将 Handoff 标记为 </span><code dir="ltr"><span>ACCEPTED</span></code><span>。</span></p><h3 dir="auto"><span>10.1 Meaning of ACCEPTED</span></h3><p dir="auto"><code dir="ltr"><span>ACCEPTED</span></code><span> 只表示接替 Agent 已理解并接受接手工作。</span></p><p dir="auto"><span>它不代表：</span></p><ul data-spread="false"><li><p dir="auto"><span>原有实现已经正确。</span></p></li><li><p dir="auto"><span>原有实现已经通过验证。</span></p></li><li><p dir="auto"><span>Task 已经完成。</span></p></li><li><p dir="auto"><span>所有遗留问题已经解决。</span></p></li></ul><h2 dir="auto"><span>11. Relationship with Other Framework Mechanisms</span></h2><h3 dir="auto"><span>11.1 Task Protocol</span></h3><p dir="auto"><span>Task Protocol 定义 Task 的目标、范围、交付物和验收规则。</span></p><p dir="auto"><span>Handoff 负责移交 Task 尚未完成的工作，不改变 Task 的正式定义。</span></p><h3 dir="auto"><span>11.2 Task State Machine</span></h3><p dir="auto"><span>Handoff 和 Task 具有独立生命周期。</span></p><p dir="auto"><span>Handoff 的创建、准备或接受，不自动改变 Task 的状态，也不构成 Task 启动授权、完成验收或重新打开 Task 的依据。</span></p><p dir="auto"><span>Task 状态必须按照 Task State Machine 管理。</span></p><h3 dir="auto"><span>11.3 Work Step Protocol</span></h3><p dir="auto"><span>Work Step 记录 Task 内部的执行步骤和进度。</span></p><p dir="auto"><span>Handoff 只需要记录未完成的 Work Steps 及其当前状态，不取代 Work Step 的正式记录。</span></p><h3 dir="auto"><span>11.4 Task Card</span></h3><p dir="auto"><span>Task Card 持续维护 Task 状态和执行进度，并关联 Handoff Documents。</span></p><p dir="auto"><span>Handoff Document 保存交接发生时的状态快照及交接所需的详细信息。</span></p><h3 dir="auto"><span>11.5 Memory</span></h3><p dir="auto"><span>Memory 用于保存可复用知识和长期上下文。</span></p><p dir="auto"><span>Memory 不替代 Handoff Document，也不承担正式交接职责。</span></p><h3 dir="auto"><span>11.6 Project Baseline</span></h3><p dir="auto"><span>正式需求、架构、接口和技术决策应保存在相应的 Project Baseline 文档中。</span></p><p dir="auto"><span>Handoff 可以引用这些文档，但不得通过 Handoff 擅自修改正式项目结论。</span></p><h3 dir="auto"><span>11.7 Approval Protocol</span></h3><p dir="auto"><span>Handoff 本身不构成 Approval，也不授予新的审批权限。</span></p><p dir="auto"><span>涉及正式需求、架构、技术路线或其他需要批准的变更时，仍然必须遵循 Approval Protocol。</span></p><h2 dir="auto"><span>12. Completion Criteria</span></h2><p dir="auto"><span>一次 Handoff 在满足以下条件时视为完成：</span></p><ul data-spread="false"><li><p dir="auto"><span>Handoff Document 已创建。</span></p></li><li><p dir="auto"><span>Handoff 状态已达到 </span><code dir="ltr"><span>ACCEPTED</span></code><span>。</span></p></li><li><p dir="auto"><span>接替 Agent 已完成必要的交接核对。</span></p></li><li><p dir="auto"><span>发现的重大差异和无法确认事项已经按照规定向 Owner 报告，并根据 Owner 的处理决定完成必要核对。</span></p></li></ul><p dir="auto"><span>Handoff 完成不代表所属 Task 完成。</span></p><p dir="auto"><span>Task 仍然按照 Task Protocol 独立推进和验收。</span></p></div></div></div></div></div></div></div>
